  disabled state too

  reproducing the exact reported scenario (a profile named "GenAI Evidence Hub") rather
  than just reasoning about it — then re-ran the full existing test suite to confirm

## 1.2.0 — Visual identity
**2026-09-21**

A full reskin against a reference brand sheet — palette, typography, logo, and icon —
plus two leftover pre-triageQ references caught in the process.

- New `branding.py`: palette constants, bundled-font loading, and asset paths, kept
  separate from `app.py` rather than inlined
- **Palette** sampled directly from the brand sheet's color swatches (exact hex, not
  estimated) and applied throughout: Deep Blue for chrome (the header rule and every
  dialog's dark title bar, previously near-black), Brand Blue for primary buttons and
  interactive accents (previously near-black too), Teal for informational console tags,
  Amber for accent text/fills on dark bars and selection/progress (distinct from, though
  visually adjacent to, the verdict amber). **Verdict colors (INCLUDE/EXCLUDE/
  MANUAL_REVIEW green/red/amber) were deliberately left unchanged** — kept the stoplight
  rather than trading instant legibility for palette purity
- New Lavender-based "nuance" tokens, applied to the criteria compiler's notes banner —
  decoupled from the verdict-amber tokens it previously borrowed, since "read these
  inferred rules" and "this paper's verdict" are different concepts that happened to share
  a color by coincidence, not intent
- **Typography: real Inter font files bundled**, not a CDN reference — a live font-CDN
  link is an HTML/CSS mechanism with no equivalent in a Tkinter desktop app. Downloaded
  Inter's actual OFL-licensed files from Google's fonts repository and loads them privately
  for the running process on Windows (`AddFontResourceExW`, `FR_PRIVATE` — no install, no
  admin rights, nothing left behind on exit); detects and uses an existing system install
  on macOS/Linux, and falls back cleanly to a close system font everywhere else. All ~96
  hardcoded font-family references across `app.py` now resolve through one shared value
  instead of being hardcoded per-widget
- **Logo and icon assets generated properly, not just dropped in**: keyed the wordmark
  logo's background transparent with feathered edges (checked against both light and dark
  test backgrounds — confirmed the header needs to stay light, since the wordmark's own
  text is dark navy and disappears against a dark background), and rendered the icon crop
  into a proper multi-resolution `.ico` (16–256px) for the window/taskbar icon instead of
  scaling a single raster down
- Main header rebuilt around the actual logo image on a light background with a Deep Blue
  rule beneath it, replacing the old plain-text wordmark on a near-black bar (with a
  graceful text fallback if the image asset is ever missing)
- Added a **Learning Data Insights credit**: a small Deep-Blue-badged version of the LDI
  mark (the source file is white-on-transparent, composited onto a colored circle for
  visibility on light surfaces) in the header and, with the fuller line "AI-assisted
  application built by Learning Data Insights," in the About card
- **Two leftover pre-rebrand references caught during this pass, neither related to the
  branding work itself:**
  - "Learning Data Insights, LLC" was still hardcoded in the header footer — missed by the
    1.0.0 rebrand because that pass searched for "GenAI Evidence Hub" / "genai", not a
    company name. Replaced by the credit line above
  - Re-confirmed "GenAI Evidence Hub" itself is fully absent — a fresh full-repo grep
    across every file turned up zero matches, consistent with it having been fixed in the
    very first 1.0.0 rebrand pass
- **Bug fix, found during this release's own testing:** a blanket find-and-replace while
  wiring up the new font system had clobbered its own `FONT_FAMILY = "Helvetica"` default
  into a self-referential `FONT_FAMILY = FONT_FAMILY`, which would have crashed the app
  immediately on import. Caught by a syntax/smoke test before packaging, not after
- Verified visually, not just by code review: rendered the app under a virtual display and

## 1.1.1 — Batch save-failure handling
**2026-09-21**

Reported from real use: a batch run on Windows hit `[Errno 13] Permission denied` writing
`paper_repository.csv` on several rows in a row, with only the raw errno shown.

- **Root cause identified, not just patched around:** the repository CSV had been open in
  Excel (or a similar program) while the batch ran. Windows gives such a program an
  exclusive lock, so triageQ's write failed outright — a config or code problem it was not.
  `paper_repository.json` (the source of truth) is written before the CSV mirror is
  regenerated, so no analysis result was actually lost in the reported run; only the CSV
  was left stale until the next successful save
- New `_friendly_save_error()` names this specific, common cause directly — "it looks like
  the file is open in another program (often Excel)... your analysis result itself was not
  lost" — instead of surfacing `[Errno 13]` unexplained. Used in both the batch log and the
  single-paper error dialog
- **Fixed a real double-counting bug found while tracing the report:** a row whose verdict
  was reached but whose save then failed was being tallied as both a completed
  INCLUDE/EXCLUDE/MANUAL_REVIEW *and* an error, because the recommendation counters
  incremented before the save was attempted. They now increment only after
  `save_to_repository` actually succeeds, so a failed-save row counts once, as an error
- Verified against the exact reported scenario: a batch run with `save_to_repository`
  raising the same `PermissionError` mid-run — confirmed the failing row is excluded from
  the repository (not partially written), the other rows save normally, the log shows the
  friendly message, and the final tally no longer double-counts (`Include: 2, Errors: 1`
  for a 3-row batch with one induced failure, not `Include: 3, Errors: 1`)

## 1.1.0 — Pluggable model providers
**2026-09-21**

triageQ was built with Claude, but nothing about its screening or criteria-compiler
prompts is Claude-specific — they're plain text, generated entirely from the active
criteria profile. This release makes that explicit: model choice is now a Settings
selection, not a hardcoded SDK call.

- New `model_providers.py`: a small provider abstraction behind which `app.py` and
  `criteria_profiles.py` now exclusively operate. Three providers ship:
  - **Anthropic** — native PDF vision via Claude's `"document"` content block, same as
    before
  - **OpenAI** — native PDF vision via the Chat Completions API's `"file"` content block
    (`file_data` as a base64 data URL) on a vision-capable model
  - **OpenAI-compatible** — any server implementing OpenAI's `/chat/completions` API:
    self-hosted model servers (vLLM, llama.cpp, LM Studio, Ollama's OpenAI shim) and
    hosted aggregators (OpenRouter, Together, Groq, etc.), configured with a base URL
    instead of a fixed host
- **PDF vision is provider-dependent, and that's tracked, not hidden.** Only Anthropic and
  OpenAI can read a PDF's own layout, figures, and tables natively. Every OpenAI-compatible
  endpoint is treated as text-only by design — there's no reliable cross-server standard
  for PDF input, so rather than guess at a given server's capabilities, triageQ extracts
  the PDF's text locally (`pypdf`, already a dependency) and screens from that instead. A
  new `pdf_vision_used` column records which happened on every record, kept deliberately
  separate from `screening_basis` (which already means something else: how much of the
  paper was available, not how the available part reached the model)
- Settings' API Key card replaced with a **Model Provider** card: a dropdown between the
  three providers, with per-provider fields (key/model for Anthropic and OpenAI; base
  URL/key/model for OpenAI-compatible) that show and hide based on selection, and a live
  note on whether the active provider supports native PDF vision. API keys remain
  in-memory only and per-provider — switching providers mid-session doesn't lose whichever
  key you'd already entered for the other one, but nothing is written to disk, matching
  the existing key-handling behavior
- `analyze_paper()` and the criteria compiler (renamed `compile_criteria_with_claude` →
  `compile_criteria`) both now take a `ProviderConfig` instead of a raw Anthropic API key,
  and route every screening and compile call through whichever provider is active
- `requirements.txt`: `anthropic` is no longer a hard dependency; both `anthropic` and
  `openai` are documented as install-what-you-use, since each is imported lazily only when
  its provider is actually selected
- README: new "Choosing a model provider" section documenting the PDF-vision trade-off,
  each provider's setup, and provider-specific troubleshooting; updated every section that
  assumed a single Anthropic-only setup
- Tested with mocked unit tests against all three providers' request shaping (content-block
  formats, parameter names, the placeholder-key handling for local servers that ignore
  auth), a real-PDF test of the text-extraction fallback, and a full run of the existing
  Xvfb-based dialog/profile test suite after the refactor — plus new tests specifically for
  the provider dropdown (field visibility, settings persistence, per-provider key isolation
  across switches) and for `analyze_paper()`'s routing logic (confirming a vision-capable
  provider receives raw PDF bytes, a text-only provider receives extracted text and never
  sees bytes, and the repository entry records both correctly). One real bug was caught and
  fixed in the process: the provider dropdown's `.set()` call was overwriting the internal
  provider-key variable with its display label instead of the underlying key

## 1.0.0 — Public release: triageQ
**2026-09-21**

The project's first public release: a full rebrand and cleanup of the final internal build
(0.1.8) for open, general-purpose use. No functional changes beyond what's listed here — the
local file library and everything else from 0.1.8 carries forward unchanged.

- Renamed the project to **triageQ** throughout: window title, header, settings file
  (`~/.triageq_settings.json`), default repository directory (`~/triageq`), outbound
  User-Agent sent to Unpaywall/OpenAlex, module docstrings, README, and this changelog
- Files un-versioned: `app_v18.py` → `app.py`, `requirements_v18.txt` → `requirements.txt`,
  `README_v18.md` → `README.md`
- **Removed the built-in default criteria profile.** triageQ now ships with no criteria of
  its own — a fresh install starts with no active profile, the header and screening tabs
  say so plainly, and Analyze / Run Batch Analysis refuse to run until a profile is created
  or imported. This replaces the previous behavior of seeding a project-specific profile to
  disk on first run
- Added an **About card** under Settings with the AI-development disclosure (built with
  Claude Sonnet 5; experimental, first-pass-only; human review expected) and the CC BY-SA
  4.0 license notice; mirrored at the top of the README
- Fixed a **Batch Upload layout bug**: the tab's content — including the log — could run
  off the bottom of the window on shorter screens with no way to reach it. The whole tab is
  now wrapped in the same scrollable-canvas pattern already used on the Settings tab
- README rewritten: removed all project-specific criteria documentation (the old "built-in
  profile" section), added a worked "Getting started: your first profile" example using
  generic, illustrative criteria, and updated every stale path/filename reference
- Confirmed no hardcoded personal name, email address, or file path existed anywhere in the
  codebase — the contact-email and repository-location fields were already blank,
  user-entered settings
- **Bug fix, found during release testing:** the "Review Compiled Criteria" / "Edit
  Criteria" dialog crashed with a `TclError` any time it had compiler notes to show — the
  notes banner passed an asymmetric `pady` tuple as a widget-constructor argument, which
  Tkinter only accepts on `pack()`/`grid()`, not on the widget itself. This is the dialog
  every new profile passes through, compiled or imported, so it was exercised end-to-end
  under a virtual display (Xvfb) as part of this release: profile creation from pasted
  text, JSON import, duplication, switching the active profile, and deleting profiles down
  to zero (confirming the app returns cleanly to the no-profile state introduced above,
  with no crash and no stale reference to a deleted profile)

## 0.1.8 — Local file library
**2026-08-13 – 2026-08-14**

- New `local_library.py`: matches local PDF/PPTX files to CSV rows by content — DOI, title
  text, or filename resemblance — never by relying on filenames to carry meaning
- Tiered confidence system (HIGH/MEDIUM/LOW/NONE): only deterministic identifier matches
  auto-accept; fuzzy matches require human confirmation before anything is screened
- Bijective assignment (one file per row, one row per file), greedy scored candidate
  matching; near-ties and author conflicts are forced into review rather than resolved
  automatically; DOI matches are exempt from author-conflict demotion
- PowerPoint decks accepted and screened as `screening_basis="slides"`; optional
  conservative mode turns omissions into UNCLEAR rather than NO
- New review dialog for confirming ambiguous matches, with per-file evidence and manual
  reassignment
- `file_mapping_log.csv` audit trail in the repository folder; mappings exportable as a
  filled-in batch CSV for exact reruns
- Batch pipeline redesigned into a single pass with explicit source precedence per row:
  URL → verified `file_path` → confirmed folder-scan match → abstract-only fallback —
  replacing an earlier separate "pre-flight" step that ran before the online retrieval it
  depended on
- Shared DOI parsing extracted into `doi_utils.py`, removing duplicate logic that had been
  copied between `pdf_resolver.py` and `local_library.py`
- `pypdf` dependency clarified: it verifies local-file identity, independent of the
  screening pipeline itself, which sends raw PDF bytes to the API directly

## 0.1.7 — Configurable criteria + automated PDF retrieval
**2026-08-12**


- Replaced hardcoded screening logic with a **criteria profile** architecture —
  inclusion/exclusion rules, prompt rendering, decision logic, CSV shape, and output schema
  all derive from a structured JSON profile (new `criteria_profiles.py`)
- Built compiler flow: raw text → Claude-compiled draft → **mandatory human review** before
  use; validator enforces that every criterion must carry `exclude_if` conditions before it
  can be saved
- Profile versioning **forks rather than overwrites** when a profile is edited after use
- Added a local decision-rule engine that recomputes recommendations post-API-call,
  preventing model drift from silently affecting the repository
- New PDF resolution waterfall (new `pdf_resolver.py`): direct link → arXiv → Unpaywall →
  OpenAlex → Semantic Scholar → Europe PMC → `citation_pdf_url` scraping, with per-source
  toggles, session-level DOI caching, and rate limiting
- Added abstract-only fallback mode (forces UNCLEAR verdicts on anything not explicitly
  stated, by design produces a higher `MANUAL_REVIEW` rate)
- README and requirements rewritten to document the profile system and a full schema
  reference

## 0.1.5 — Decision-order bug fix and cleanup
**2026-08-12**

- **Root-cause fix:** `overall_recommendation` moved to the *last* field in the JSON output
  schema. Previously the model committed to a verdict before reasoning through the
  criteria, occasionally self-correcting in the notes fields without being able to revise
  the recommendation it had already written. Ordering the schema so the verdict comes last
  forces full analysis first
- Fixed trailing-comma JSON parse failures with a regex cleanup pass before parsing
- Removed six pieces of accumulated dead code: an unused `io` import, an unused palette
  key, a dead `if False` branch, a stale exception handler left over from a removed local
  backend, an unused tuple element, and a duplicated sort-key function (extracted to one
  shared implementation)
